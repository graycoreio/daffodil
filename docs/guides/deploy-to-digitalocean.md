# Deploy a Daffodil storefront to DigitalOcean App Platform

This tutorial takes you from a new Angular application to the Daffodil commerce demo running as a Node.js web service on DigitalOcean App Platform. It uses server-side rendering (SSR) and the demo's in-memory driver, so no commerce backend is required.

This approach builds the Angular storefront, serves its browser assets, and sends page requests through a running Node server. App Platform manages the service; you do not need to provision a Droplet or write a Dockerfile. A Magento or other commerce backend remains a separate service.

## Prerequisites

- Node.js 24.13.1 or later within Node 24, with npm 11.
- Git and a repository on a Git provider supported by App Platform.
- A DigitalOcean account with permission to create an App Platform web service. Review the selected service's cost before creating it.

This walkthrough uses Angular CLI **21.2.31** and Daffodil **0.94.1**, matching the Netlify tutorial. Daffodil 0.94.1 requires Angular 21. Keep these versions together when following the example.

## 1. Create the demo storefront

```bash
npx @angular/cli@21.2.31 new daffodil-digitalocean --style=scss --routing=true --ssr=true --zoneless=false --package-manager=npm --defaults
cd daffodil-digitalocean
npx ng add @daffodil/commerce@0.94.1 --driver=demo --is-new-project --skip-confirmation
npm start
```

Open `http://localhost:4200` and confirm that the Daffodil homepage and sample products appear. Leave **In-Memory Driver** selected, then stop the development server with `Ctrl+C`.

## 2. Set the runtime and production command

Run these commands from the application directory:

```bash
npm pkg set 'engines.node=24.x' 'engines.npm=11.x'
npm pkg set 'scripts.start:ssr=node dist/daffodil-digitalocean/server/server.mjs'
npm install --package-lock-only
```

App Platform reads the Node and npm versions from `package.json`. Commit `package-lock.json` and keep one package-manager lockfile for this example. The Node buildpack installs dependencies and removes development dependencies after building; packages needed by your running server must be available in production. See the [Node.js buildpack documentation](https://docs.digitalocean.com/products/app-platform/reference/buildpacks/nodejs/).

`npm start` remains the Angular development command. The hosted service will use `npm run start:ssr`, which starts the compiled application.

## 3. Configure rendering and HTTP requests

Replace `src/app/app.routes.server.ts` with:

```typescript
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  { path: '**', renderMode: RenderMode.Server },
];
```

Keep the generated `provideServerRendering(withRoutes(serverRoutes))` registration in `app.config.server.ts`. Rendering on request avoids trying to discover all dynamic product URLs at build time. See [Angular's server rendering guide](https://angular.dev/guide/ssr).

In `src/app/app.config.ts`, extend the existing HTTP import and update the existing provider:

```typescript
import { provideHttpClient, withFetch } from '@angular/common/http';

// Inside the existing providers array:
provideHttpClient(withFetch()),
```

Retain the other providers generated by Daffodil.

## 4. Configure the Node server

Replace `src/server.ts` with:

```typescript
import {
  AngularNodeAppEngine,
  createNodeRequestHandler,
  createWebRequestFromNodeRequest,
  isMainModule,
  writeResponseToNodeResponse,
} from '@angular/ssr/node';
import express from 'express';
import { join } from 'node:path';

const app = express();
const browserDistFolder = join(import.meta.dirname, '../browser');
const publicOrigin = process.env['PUBLIC_ORIGIN']
  ? new URL(process.env['PUBLIC_ORIGIN'])
  : undefined;
const preventIndexing = process.env['PREVENT_INDEXING'] === 'true';
const angularApp = new AngularNodeAppEngine({
  allowedHosts: publicOrigin ? [publicOrigin.hostname] : ['localhost', '127.0.0.1'],
  trustProxyHeaders: false,
});

app.get('/healthz', (_req, res) => {
  res.set('Cache-Control', 'no-store').status(200).send('ok');
});

app.use((req, res, next) => {
  if (preventIndexing) {
    res.set('X-Robots-Tag', 'noindex, nofollow');
    if (req.path === '/robots.txt') {
      res.set('Cache-Control', 'no-store').type('text/plain')
        .send('User-agent: *\nDisallow: /\n');
      return;
    }
  }
  next();
});

app.use(express.static(browserDistFolder, {
  index: false,
  redirect: false,
}));

app.use(async (req, res, next) => {
  try {
    const incoming = createWebRequestFromNodeRequest(req, false);
    const url = new URL(incoming.url);
    const request = publicOrigin
      ? new Request(`${publicOrigin.origin}${url.pathname}${url.search}`, incoming)
      : incoming;
    request.headers.set('host', new URL(request.url).host);
    for (const name of [...request.headers.keys()]) {
      if (name.startsWith('x-forwarded-')) request.headers.delete(name);
    }
    const response = await angularApp.handle(request);
    if (response) {
      response.headers.set('Cache-Control', 'no-store');
      await writeResponseToNodeResponse(response, res);
    } else {
      next();
    }
  } catch (error) {
    next(error);
  }
});

if (isMainModule(import.meta.url)) {
  const port = Number(process.env['PORT'] ?? 8080);
  app.listen(port, '0.0.0.0', (error) => {
    if (error) throw error;
    console.log(`Storefront listening on port ${port}`);
  });
}

export const reqHandler = createNodeRequestHandler(app);
```

The server binds to `0.0.0.0` on `PORT`, serves static files before rendering pages, and provides `/healthz` for readiness checks. The health endpoint checks that the process is serving requests; it does not prove that Angular rendering or a remote backend is healthy.

`PUBLIC_ORIGIN` is the public HTTPS origin, such as `https://your-app.ondigitalocean.app`. It sets the URL Angular sees and the allowed rendering hostname. Without it, this example permits local development hosts. It does not automatically add canonical or social metadata to the demo, but supplies the correct origin to application code that generates them.

The request adapter preserves the incoming method, application headers, and body. It aligns the Host header with the configured origin and removes forwarded headers before Angular validates the request. This matters when you later add API handling. The example uses a configured public origin rather than trusting arbitrary forwarded-host headers, and marks rendered responses `no-store` until you introduce an appropriate caching policy.

`PREVENT_INDEXING=true` adds a noindex header and a disallow-all `robots.txt` for the demo or staging service. This is a search-engine instruction, not access control.

## 5. Build and test the production server locally

In `angular.json`, under `projects.daffodil-digitalocean.architect.build.configurations.production.budgets`, update only the entry with `"type": "initial"`:

```json
{
  "type": "initial",
  "maximumWarning": "1.2MB",
  "maximumError": "1.5MB"
}
```

The multi-driver demo is approximately 1.09 MB before transfer compression, exceeding Angular's default 1 MB error threshold. Retain the component-style budget and reassess the initial budget as you replace demo features.

Build and start the compiled server:

```bash
npm run build
PORT=8080 PUBLIC_ORIGIN=http://localhost:8080 PREVENT_INDEXING=true npm run start:ssr
```

The environment-variable syntax above is for macOS/Linux shells. On Windows, set the same variables using your shell's syntax before running the command.

Open `http://localhost:8080`. In another terminal:

```bash
curl -i http://localhost:8080/healthz
curl -I http://localhost:8080/
curl http://localhost:8080/robots.txt
```

Expect HTTP 200 with `ok` from `/healthz`, `X-Robots-Tag: noindex, nofollow` on the homepage, and `Disallow: /` in `robots.txt`. View the homepage's original source and check for “Build a storefront that connects to” to verify SSR. A successful development-server check alone does not test the compiled server.

The output should include both `dist/daffodil-digitalocean/browser` and `dist/daffodil-digitalocean/server`. Zero prerendered routes is expected. Stop the server with `Ctrl+C` when finished.

## 6. Create the App Platform service

Commit the application and push it to your Git provider. Include the lockfile and server changes; exclude `node_modules` and `dist`.

In DigitalOcean, choose **Create → App Platform**, connect the repository, and select the branch to deploy. Configure the component as a **Web Service** using the Node.js buildpack. A Static Site component cannot run this SSR server. Follow the [App Platform creation flow](https://docs.digitalocean.com/products/app-platform/how-to/create-apps/).

| Setting | Value for this tutorial |
| --- | --- |
| Source directory | Repository root (`/`) |
| Resource type | Web Service |
| Build command | `npm run build` |
| Run command | `npm run start:ssr` |
| Public HTTP port | `8080` |
| HTTP route | `/` |
| HTTP health-check path | `/healthz` |

The run command starts an existing build. Do not use `ng serve` or build the application each time the service starts. There is no static-site publish directory to configure for this web service. See [build and run commands](https://docs.digitalocean.com/products/app-platform/how-to/build-run-commands/).

Add these component environment variables with **Run Time** scope:

| Key | Value |
| --- | --- |
| `PORT` | `8080` |
| `PUBLIC_ORIGIN` | `${APP_URL}` |
| `PREVENT_INDEXING` | `true` |
| `NODE_ENV` | `production` |

Enter `${APP_URL}` literally in DigitalOcean's value field. It is a bindable variable that resolves to the application's primary public URL. No commerce credentials are needed for the in-memory demo. See [App Platform environment variables](https://docs.digitalocean.com/products/app-platform/how-to/use-environment-variables/).

Configure the HTTP readiness probe to request `/healthz` on the service port. Depending on the creation screen, you may need to set this in the component's settings after creation. The default TCP probe can verify the listener until then. See [health-check configuration](https://docs.digitalocean.com/products/app-platform/how-to/manage-health-checks/).

Select the region and service size, review the displayed cost, then create the app. Inspect both build and runtime logs. The build should finish successfully, and the runtime should report `Storefront listening on port 8080`. A successful build followed by a failed health check usually points to the run command, port, or startup configuration.

## 7. Verify the hosted demo

Use the `https://<app-name>.ondigitalocean.app` URL from the app overview:

- Request `/healthz` and confirm HTTP 200 with `ok`.
- Open the homepage, refresh it, and confirm that products and images load.
- Inspect the original homepage HTML for the visible heading to confirm SSR, and check the browser console for errors.
- Open a product through the homepage's links and confirm that client-side navigation works.
- Check the noindex header and `robots.txt` on the hosted domain.
- Inspect a JavaScript or stylesheet request to confirm that the Node service serves static assets successfully.

The in-memory driver regenerates temporary sample products and URLs. In this demo version, reopening a product URL in a new application instance can show the application's 404 page. After connecting a persistent commerce backend, verify direct product links and refreshes against its stable URLs as well.

For a customer-facing domain, add it through [App Platform's domain settings](https://docs.digitalocean.com/products/app-platform/how-to/manage-domains/) and verify HTTPS and `PUBLIC_ORIGIN`. Before setting `PREVENT_INDEXING=false`, redirect the starter domain to the primary domain or implement a host-specific indexing policy. This sample's environment flag applies to the entire service; Breeze uses a host-specific policy.

## Applying the guide to an existing storefront

### Source directory and run command

In a monorepo, the frontend might live in `frontend/project-name`. When deploying that checkout, select this source directory so the build uses the frontend's package manifest and lockfile. If deploying a repository with the frontend at its root, use `/` instead. Paths must match the repository you import. Files outside a selected source directory are unavailable at runtime; see [deploying from monorepos](https://docs.digitalocean.com/products/app-platform/how-to/deploy-from-monorepo/).

### Backend requests and public URLs

Angular's development proxy does not configure deployed API routes. If you proxy `/graphql` and `/rest` through a server handler before page rendering, the Node host must preserve POST bodies, `Content-Type`, authorization, store headers, cookies, and separate `Set-Cookie` response headers. Rendering the homepage successfully does not prove that sign-in or cart mutations work.

When adapting an existing storefront, verify a harmless backend query through the deployed frontend and test authentication and mutations in a test environment. If the proxy uses `fetch`, account for decompressed response bodies rather than forwarding stale encoding and length headers. Use a fixed trusted backend, not a destination supplied by the browser.

Set `PUBLIC_ORIGIN` to the service's public origin and inspect generated canonical, Open Graph, and structured-data URLs. Breeze previously emitted `localhost:8080` URLs until its host reconstructed the public request origin correctly.

### Platform-specific features

App Platform does not execute Netlify configuration, Edge Functions, or Netlify Functions. Image CDN URLs, editor-save functions, cache purges, redirects, and staging indexing rules need an equivalent implementation on the selected host. Breeze's Node host redirects its Netlify image endpoint to the original image; that fallback does not perform Netlify image optimization. The basic demo above does not require those Breeze-specific services.

Build-time variables do not automatically become Angular browser configuration. Keep private credentials out of client bundles and distinguish build-time configuration from server runtime settings. Avoid shared caching of authenticated or cart-dependent HTML until the policy has been designed and tested.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Build passes but deployment fails its health check | Use the production run command, listen on `0.0.0.0`, and match `PORT` to the public HTTP port. |
| The process exits immediately | Ensure the chosen entry point starts a listener; Breeze's exported handler needs `ssr:host`. |
| Angular CLI is unavailable when the service starts | Start compiled output, not `ng serve`; build tools may be removed after the build. |
| Peer dependencies conflict | Keep Angular 21 with Daffodil 0.94.1 for this walkthrough. |
| Initial bundle exceeds the build budget | Apply the measured demo budget in step 5. |
| Host validation fails or pages fall back to client rendering | Check `PUBLIC_ORIGIN` and the allowed hostname. Do not disable host validation globally. |
| Metadata contains localhost or HTTP URLs | Verify the public HTTPS origin supplied to the renderer. |
| Pages work but API POSTs fail | Check deployed proxy routing and preservation of request headers and bodies. |
| Demo product refresh returns 404 | The in-memory data is temporary; repeat the stable-link check with a persistent backend. |
| Netlify function or image URLs fail | Provide an equivalent on App Platform or remove the platform-specific dependency. |
