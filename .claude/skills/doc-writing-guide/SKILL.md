# Daffodil documentation writing guide

Daffodil docs are generated by [dgeni](../../../tools/dgeni/README.md) from markdown and TypeScript in this repo, then served by the `@daffodil/daffio` app. This skill covers how to write that content and the rules the pipeline enforces.

## I. Writing style

### Tone and content

- **Be direct and friendly.** Professional, not casual. Skip filler ("simply", "just", "easy").
- **Write for a global audience.** Many readers are not native English speakers. Prefer common words and short sentences.
- **Lead with the reader's task.** Explain what they need to do and why before how the internals work.
- **Don't pre-announce.** Don't document unreleased features or make claims the code doesn't back up.
- **Use descriptive link text.** Link text names the destination. Never "click here" or "this link".

### Language and grammar

- **Second person.** Address the reader as "you".
- **Active voice.** "The driver sends the request", not "The request is sent".
- **American English** spelling and punctuation.
- **Conditions first.** "If you use Magento, set up fragment introspection."
- **Define terms on first use**, including acronyms (for example, "Google Tag Manager (GTM)").
- **One term per concept.** Daffodil terms to use consistently: _driver_, _facade_, _state_, _in-memory driver_, _testing driver_, _factory_, _platform_ (for Magento, Shopify, etc.).
- **One idea per sentence.**

### Formatting

- **Sentence case headings.** Capitalize only the first word and proper nouns: "Fragment introspection", not "Fragment Introspection".
- **Lists:** numbered for sequential steps, bullets for unordered items, tables for attribute/option/term pairs.
- **Oxford comma.**
- **Code font** for code-related text: package names (`@daffodil/cart`), symbols, file names, commands, attributes, and selectors.
- **Bold** only for UI labels the reader will see.
- **Dates:** "September 4, 2024", never "9/4/2024".

### Code samples

- Code must compile against the current public API. Import from public entry points (`@daffodil/cart/state`, never deep `src/` paths).
- Prefer current Angular idioms: standalone components, `inject()`, and `provide*` functions. Only show `NgModule` setup when the package has no standalone API, or in a deprecation notice.
- Show imports for every Daffodil symbol in a TypeScript sample.
- Comments explain _why_, not _what_.

## II. Where docs live and how they render

| Source                                           | Rendered as                                                       |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| `docs/guides/**/*.md`                            | Top-level guides at `/docs/guides/...`                            |
| `docs/explanations/**/*.md`                      | Explanations (architecture, concepts) at `/docs/explanations/...` |
| `libs/<pkg>/README.md`                           | Package landing page at `/docs/packages/<pkg>`                    |
| `libs/<pkg>/guides/**/*.md`                      | Package guides at `/docs/packages/<pkg>/...`                      |
| `libs/design/<component>/README.md`              | Design component page at `/docs/design/components/<component>`    |
| `libs/design/guides/**/*.md`                     | Design guides at `/docs/design/...`                               |
| `libs/storefront/...`                            | Same structure as design, under `/docs/storefront/...`            |
| JSDoc on exported symbols in `libs/<pkg>/**/src` | API reference at `/docs/api/...`                                  |
| `docs/internal/**`                               | Contributor docs. **Not** published.                              |

Packages marked `"private": true` in their `package.json` are excluded from the generated docs.

### Titles

Every published markdown file **must** start with a single `# Title` line. dgeni reads the title from the first `#` heading and the build fails without one.

- Package READMEs use the package name: `# @daffodil/cart`.
- Design component READMEs use the component name: `# Button`.
- Guides use a short task or topic name: `# Drivers`, `# Fragment introspection`.

### Headings

- Use `##` and `###` for structure. Don't skip levels.
- Heading text becomes the anchor id (via `markdown-toc`'s `slugify`) and appears in the page's table of contents. Keep headings short and stable, since other docs link to them.

### Navigation order (`index.json`)

Some guide directories contain an `index.json` that orders their nav entries, for example `docs/guides/index.json`:

```json
["introduction", "getting-started", "essentials"]
```

Entries are file names without `.md` or subdirectory names. **When a directory has an `index.json`, every page and subdirectory in it must be listed**, or the docs build throws `Sort data does not contain a reference to <id>`. When you add, rename, or remove a page in such a directory, update its `index.json`.

### Links

Link to other docs by their **repo-root-relative file path**. dgeni rewrites these to site URLs, so links stay valid when routes change.

```markdown
Refer to the [fragment introspection guide](/tools/builders/guides/fragment-introspection.md).
See the [configuration guide](/libs/analytics/guides/configuration.md#configuring-analyzeableactions).
```

- Always start with `/` and include the `.md` extension.
- Anchors use the slugified heading text.
- Don't hardcode `daff.io` URLs or `/docs/...` routes for internal pages.
- External links are fine as full URLs.

### Symbol auto-linking

Any word inside inline code or a `ts`/`typescript` code block that matches an exported Daffodil symbol is automatically linked to its API page. Write the exact symbol name in backticks, `DaffCartFacade`, and don't add a manual link to the API page. `{@link}` does **not** work in markdown files, only in JSDoc.

### Code blocks

Highlighting is done with highlight.js, and only these languages are registered:

| Use                        | Fence                                                               |
| -------------------------- | ------------------------------------------------------------------- |
| TypeScript                 | `ts` (preferred; `typescript` also works). Symbols are auto-linked. |
| Angular templates and HTML | `html`                                                              |
| Styles                     | `scss`                                                              |
| Terminal commands          | `bash`                                                              |
| GraphQL                    | `graphql` or `gql`                                                  |

Anything else, including `json`, `yaml`, and `shell`, renders as plain text. That's acceptable for JSON or YAML, but use `bash` for commands, not `shell` or `sh`.

Show install commands for both npm and yarn, matching existing package READMEs:

````markdown
Install with npm:

```bash
npm install @daffodil/cart --save
```

Install with yarn:

```bash
yarn add @daffodil/cart
```
````

There is no code block metadata (no titles, line highlighting, or file includes). Put the file name in the sentence before the block if it matters.

### Notes and callouts

Use a blockquote with a bold label:

```markdown
> **Note:** Only set up one `@daffodil/cart` driver in the root component at a time.

> **Important:** Fragment introspection is required for the Magento driver.

> **Deprecation notice:**
>
> `DaffButtonModule` is deprecated. Use the standalone component imports instead.
```

Use `Note`, `Important`, `Warning`, or `Deprecation notice`. Use them sparingly. If every section has a note, none of them stand out.

### Raw HTML

Markdown is parsed with `marked`, so raw HTML passes through. The only custom element supported in docs is the design example viewer (see below). Don't add other Angular components to markdown; they won't render.

Leave `<!-- TODO: ... -->` comments for missing links instead of linking to a non-existent page.

## III. Package docs

### Package README (`libs/<pkg>/README.md`)

The landing page for a package. Structure:

1. `# @daffodil/<pkg>`
2. One or two sentences on what the package does and who it's for.
3. `## Overview` (optional) for more context.
4. `## Installation` with npm and yarn commands.
5. `## Getting started`, `## Features`, or `## Drivers` linking out to the package's guides.

Keep the README short. Put detailed how-tos in `libs/<pkg>/guides/`.

### Package guides (`libs/<pkg>/guides/`)

Common guide names across packages, reuse them when they fit: `usage.md`, `state.md`, `drivers.md`, `testing.md`, `extensions.md`, `configuration.md`. Driver-specific guides go in `guides/drivers/<driver>.md`.

A `drivers.md` guide has one `##` section per driver (in-memory, Magento, Shopify, ...), each with numbered setup steps followed by a code sample.

## IV. Design component docs

Component READMEs in `libs/design/<component>/README.md` follow a fixed structure. Use these `##` sections, in this order, and leave out the ones that don't apply:

1. `# <Component>`
2. **A single-line summary directly under the title.** dgeni extracts this line as the component's description for the nav and overview cards, and removes it from the page body. It must be one line with no blank line between it and the title.
3. `## Overview`: what the component is and its variants. Usually ends with a live example.
4. `## Best practices`: when to use it and when not to.
5. `## Usage`: which constant or component to import, with a `ts` sample importing from `@daffodil/design/<component>`.
6. `## Anatomy`: an `html` sample of the full structure, followed by a bullet per part.
7. `## Features`: one `###` per feature (colors, sizes, disabled, and so on), each with a short explanation and a live example.
8. `## Accessibility`: `### Built-in behavior` (what the component handles) and `### Developer responsibilities` (what the consumer must do, such as labels or alt text).

### Live examples

Embed a running example with:

```html
<daff-docs-example-viewer example="button-types"></daff-docs-example-viewer>
```

The `example` value is an id registered in `libs/design-examples/<component>/src/provider.ts`. To add a new example:

1. Create `libs/design-examples/<component>/src/<example-id>/<example-id>.component.{ts,html,scss}`. Use selector `<example-id>-example`, class `<PascalName>ExampleComponent`, `OnPush`, and standalone imports.
2. Export the component from `libs/design-examples/<component>/src/public_api.ts`.
3. Add `{ id: '<example-id>', component: () => import(...) }` to the `provideDaffDocsExampleContent` call in `provider.ts`.
4. Reference it from the README with the viewer element.

The docs build doesn't check `example` ids, so confirm the id exists in `provider.ts` yourself.

## V. API docs (JSDoc)

API reference pages come from JSDoc on exported symbols. Every exported symbol should have one.

- **Always use multiline `/** */` blocks**, even for a one-sentence description.
- The first sentence is the summary. Say what the symbol is or does, not that it "is a class".
- Reference other symbols with `{@link DaffSymbolName}`.
- Hide public-but-internal symbols or members with `@docs-private`.
- Use `@inheritdoc` on implementations to pull member docs from the interface they implement.
- Mark deprecations with `@deprecated` plus what to use instead and when it will be removed.
- Use `@see <url>` for external references.
- Add `@example` with a caption on the same line, followed by a fenced `ts` block. Captions become headings in the page's table of contents.

````ts
/**
 * Pushes entries onto `window.dataLayer` for Google Tag Manager.
 * GTM itself is not loaded by this service.
 *
 * Usually used through {@link provideDaffDataLayerTracker}.
 *
 * @see https://developers.google.com/tag-platform/tag-manager/datalayer
 *
 * @example Pushing a virtual page view
 * ```ts
 * export class MyComponent {
 *   private dataLayer = inject(DaffAnalyticsDataLayer);
 *
 *   trackPageView() {
 *     this.dataLayer.push({ event: 'virtualPageView' });
 *   }
 * }
 * ```
 */
````

Only files under a package's `src/` (and its secondary entry points' `src/`) are read for API docs. A symbol that isn't exported from a public entry point has no API page.

## VI. Checking your work

- The docs build (`npx nx run @daffodil/tools-dgeni:build`) catches missing titles and incomplete `index.json` files. It is a build, so ask the user before running it.
- Check that every repo-relative link points at a file that exists.
- Check that every `<daff-docs-example-viewer example="...">` id is registered in the matching `provider.ts`.
- Reread headings for sentence case and new pages for an `index.json` entry.
